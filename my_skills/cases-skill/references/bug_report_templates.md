# Bug 报告模板

用于编写清晰、可复现、可执行的 Bug 文档的标准模板。

---

## 完整用例工作簿标准结构（不得随意修改或增减）
生成 Bug 报告 Excel 时，工作簿必须按照以下顺序组织：
- **报告概览**：汇总本次测试执行和 Bug 情况，包括用例总数、通过数、失败数、归并后的 Bug 数、待确认事项及各 Bug 标题。
- **bug 报告**：Sheet命名规则为BUG-[MODULE]-NNN。每个确认的 Bug 单独使用一个 Sheet 记录完整 Bug 报告。`ID` 在当前工作簿内不可重复，按顺序递增，例如 `BUG-ROLE-001`、`BUG-ROLE-002`。多条失败用例若属于同一根本问题，应归并为同一个 Bug，不得仅因用例数量重复生成 Bug。
- **待补充清单**：记录生成正式 Bug 报告时仍缺少的关键信息，例如截图、环境版本、复现率、实际结果、Network、Console 或待确认业务规则。
- **失败执行原文**：保留原测试用例文件中所有失败执行记录的原始内容，用于追溯 Bug 来源。
  - 应保留原用例编号、用例标题、前置条件、测试数据、测试步骤、预期结果、实际结果、是否通过和备注等相关字段。
  - 原始执行内容不得因生成 Bug 报告而改写。
  - 原始执行内容不得因生成 Bug 报告而改写。

除上述 Sheet 外，不得生成任何其他 Sheet，不得修改上述 Sheet 的用途。

---

### 报告概览

`报告概览` Sheet 必须使用两列表格：
| 项目 | 内容 |
|------|------|

第一列固定为“项目”，第二列固定为“内容”。
行结构及顺序固定如下，不得自行替换、重命名、删除或调整顺序：

至少包含：


| 项目 | 内容 |
|------|------|
| 文档 | [模块名称] Bug 报告 |
| 来源 | [原始测试执行文件名称及补充信息来源] |
| 有效执行用例 | [实际已执行且具有明确执行结果的用例数量] |
| 通过 | [通过用例数量] |
| 失败 | [失败用例数量] |
| 归并Bug数 | [失败用例分析并归并后的实际 Bug 数量] |
| 待确认业务规则 | [仍需确认的业务规则数量；没有则填写 0] |
| 处理说明 | [说明失败用例如何筛选、归并为 Bug，以及特殊处理情况] |
| 报告完整性 | [说明截图、环境、复现率等信息的完整情况及待补充项] |
| 源文件差异 | [说明生成 Bug 报告过程中对原执行文件的识别、修正或差异；无差异时说明“无”] |
| BUG-ROLE-001 | [BUG完整标题] |
| BUG-ROLE-002 | [BUG完整标题] |
| ... | [按照 Bug ID 顺序继续列出，数量与归并 Bug 数一致] |


失败用例数量不得直接等同于 Bug 数量。
多条失败用例属于同一问题时，应归并为一个 Bug。
---

#### Bug 列表规则

- 每个归并后的 Bug 必须在报告概览中单独占一行。
- 项目名称使用 `Bug-001`、`Bug-002`、`Bug-003`……连续编号。
- 内容填写对应 Bug 的完整标题。
- Bug 行数量必须与“归并Bug数”一致。
- 不得将多个 Bug 合并在同一个单元格中。
- `Bug-xxx` 行应放在“源文件差异”之后

## 严重程度定义

| 级别 | 判定标准 | 响应时间 | 示例 |
|-------|----------|---------------|----------|
| **严重** | 系统不可用、数据丢失、安全漏洞 | < 4 小时 | 无法登录、支付失败、数据泄露 |
| **高** | 核心功能不可用，且无临时解决方案 | < 24 小时 | 搜索不可用、结算失败 |
| **中** | 功能部分异常，但存在临时解决方案 | < 1 周 | 筛选缺少选项、加载缓慢 |
| **低** | 外观问题或极少发生的边界场景 | 下一版本 | 拼写错误、轻微对齐问题、罕见崩溃 |

## 优先级参考矩阵

|  | 低影响 | 中等影响 | 高影响 | 严重影响 |
|--|-----------|---------------|-------------|-----------------|
| **极少发生** | P3 | P3 | P2 | P1 |
| **偶尔发生** | P3 | P2 | P1 | P0 |
| **经常发生** | P2 | P1 | P0 | P0 |
| **必现** | P2 | P1 | P0 | P0 |

优先级综合考虑问题影响范围、发生频率、业务重要性和修复紧迫程度，不应仅由严重程度决定。

## Bug 标题最佳实践

**好的标题:**
- "[登录] 使用有效邮箱时未发送密码重置邮件"
- "[结算] 优惠码重复应用两次后购物车总金额显示为 $0"
- "[仪表盘] 加载超过 1000 条记录时页面崩溃"

**不好的标题:**
- "登录有 Bug"（过于模糊）
- "不能用"（缺少上下文）
- "请尽快修复！！！"（带有情绪，且没有有效信息）
- "小问题"（无法判断具体是什么问题）

## 基于测试执行结果生成 Bug

当输入文件为已执行的测试用例文件时，应优先根据测试执行结果自动识别并生成 Bug 报告。

### Bug 识别规则

- `是否通过 = 失败 / fail / failed / 不通过` 的测试用例视为 Bug 候选。
- `是否通过 = 通过 / pass / passed` 的测试用例不得生成 Bug。
- `是否通过`为空时，不得默认判定为 Bug。
- 如测试用例被标记为 `BLOCKED / 待确认 / 无法执行`，不得作为正式 Bug 生成，应进入待确认清单。

### 字段映射

生成 Bug 报告时，优先从原测试用例中提取：

| Bug 报告字段 | 测试用例来源 |
|-------------|-------------|
| Bug 标题 | 所属模块 + 用例标题 + 实际异常现象 |
| 前置条件 | 前置条件 |
| 复现步骤 | 测试步骤 |
| 测试数据 | 测试数据 |
| 预期结果 | 预期结果 |
| 实际结果 | 实际结果 |
| Bug 说明补充 | 备注 |
| 环境/版本 | 测试文件、用户提供的信息或执行环境 |
| 问题证据 | 用户提供的截图、Console、Network、日志等 |

- `实际结果`为描述 Bug 现象的主要依据。
- `备注`用于补充复现情况、异常表现、证据位置或其他执行信息，不得用备注替代实际结果。
- 不得根据“是否通过 = 失败”自行猜测具体异常现象。

### 信息不足处理

若失败用例缺少生成 Bug 所需的关键信息：

- 缺少实际结果：标记为“Bug 信息不足”，不得编造异常现象；
- 缺少预期结果：尝试从需求、测试点或规则文件中确认；仍无法确认则标记“待确认”；
- 缺少截图：提示补充截图证据；
- 缺少环境信息：保留为待补充字段，不得自行假设。

## Bug 报告生成规则
- Bug 报告必须基于实际测试现象生成，不得编造未观察到的信息。
- 截图证据为必填项；视频、Console、Network、日志等证据按问题类型填写。
- 无相关证据的按需字段直接省略，不填写“无”“N/A”等无效内容。
- 复现步骤必须具体、连续且可独立执行。
- 预期结果应基于需求、设计、业务规则或已确认的正确行为。
- 实际结果只描述实际观察到的现象，不推测根因。
- 严重程度与优先级需分别评估，不得简单等同。

## Bug 报告检查清单

提交前:
- [ ] 标题具体且具有描述性

- [ ] 预期结果与实际结果描述清晰
- [ ] 环境信息完整
- [ ] 已附上截图/证据
- [ ] 已设置严重程度/优先级
- [ ] 已检查是否存在重复 Bug
- [ ] 已关联相关项
