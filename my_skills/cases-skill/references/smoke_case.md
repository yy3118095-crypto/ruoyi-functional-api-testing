# 冒烟测试编写规则

本规则用于从 cases/ 中已有功能测试用例提取最小功能冒烟集，并在缺少接口文档时生成由 QA 补全的接口冒烟用例骨架。

## 激活方式

仅在明确调用 `$api-smoke-skill` 时执行。

## 目标

生成少量、高优先级、可快速执行的功能/接口冒烟测试，
用于验证版本部署后的核心接口和核心业务链路是否可用。

## 冒烟测试场景选择原则

冒烟测试以核心正向业务流程为主体，但不等于仅包含正向用例。

冒烟测试集应优先覆盖：

1. 系统核心入口是否可用；
2. 核心 CRUD 或主要业务操作是否可完成；
3. 核心业务链是否能够端到端执行；
4. 数据、状态和权限变化是否真正生效；
5. 会导致系统核心功能失效的关键阻断规则。

### 正向场景

核心正向主流程原则上必须纳入冒烟测试。

例如：

- 正确登录；
- 新增核心业务数据；
- 修改核心业务数据；
- 删除测试数据；
- 分配角色；
- 配置核心权限。

### 关键负向/阻断场景

仅当失败保护本身属于核心业务能力时，允许纳入少量负向场景。

例如：

- 错误认证信息不得登录；
- 禁用用户不得登录；
- 权限被移除后不得继续访问；
- 角色解绑后原权限不得继续生效；
- 退出登录后旧会话不得继续访问受保护资源。

不得将普通字段校验、低风险边界值或大量同类异常场景加入冒烟集。

例如以下场景通常不属于最小冒烟：

- 字段 N-1 / N / N+1 全边界组合；
- 多种特殊字符；
- 多种错误密码组合；
- 普通提示文案校验；
- 低风险格式校验；
- 同一业务规则的多个重复异常场景。

### 最小化原则

每加入一条冒烟用例都应回答：

> 删除该用例后，是否会导致某个核心功能、核心业务链或关键阻断能力无法得到验证？

若答案为“不会”，则该用例原则上不应进入最小冒烟集。

### 禁止按模块机械配额

不得为了保证“每个功能点都有一条用例”而机械扩充冒烟测试集。

冒烟测试关注核心可用性和主要业务链，不要求完整覆盖所有功能点、所有测试方法或所有异常类型。

完整功能覆盖应由正式功能测试集或回归测试集承担。

## 功能冒烟测试用例生成

### 输入规则

- 默认读取 `cases/*.xlsx`。
- 优先读取正式的“测试用例”工作表。
- “规则”“测试点”“追溯矩阵”和“数据准备”等工作表用于理解约束、准备数据及核对来源。
- 不得修改 `cases/` 中的源文件。

### 纳入范围

冒烟测试以核心正向业务流程为主体，同时允许纳入少量会直接影响系统可用性、认证有效性或核心权限正确性的关键阻断场景。

优先选择：

- P0 核心正向主流程；
- 会阻断后续测试或导致核心功能不可用的关键异常；
- 登录成功及认证状态建立；
- 错误认证信息被正确拒绝等关键认证阻断场景；
- 核心查询、新增、修改、删除和状态变更；
- 用户与角色等关键业务关联；
- 核心菜单、按钮或数据权限链路；
- 权限新增、移除或角色变更后的实际生效验证；
- 必要时重新登录后的权限生效或失效验证；
- 写操作后的列表、详情、状态或最终业务结果校验。

纳入负向场景时，应满足：

- 该失败保护属于核心业务能力；
- 若不验证，可能无法判断系统核心功能是否可用或安全边界是否有效；
- 同类负向场景只保留最有代表性的一条或少量关键场景，不重复铺开。

---

### 默认排除范围

默认不纳入以下场景：

- 大量边界值组合；
- 同一规则的多个重复无效等价类；
- 兼容性、易用性、性能和安全专项测试；
- 低频异常和重复验证；
- 非核心查询条件；
- 普通提示文案校验；
- 低风险格式校验；
- 批量操作；
- 非核心导入、导出功能；
- 不影响核心业务链完整性的低优先级功能。

如果用户在发送指令时明确指定某项属于核心流程、关键风险或本次发布重点，则可以纳入冒烟测试集。

### 组织规则
- 冒烟集必须形成可以按顺序执行的业务链。
- 尽量复用同一组可识别、可清理的测试数据。
- 每个核心模块至少覆盖一条正向主流程。
- 不能仅根据 P0 标签机械选择全部 P0 用例。
- 验证目标相近、失败原因仍可定位的场景可以合并。
- 权限配置必须通过目标用户重新登录，并访问已授权和未授权资源进行验证。
- 数据权限至少包含允许访问和禁止访问的对照数据。
- 保留来源功能用例编号或测试点编号。

### 功能冒烟输出字段
| 字段 | 填写规则 |
| --- | --- |
| 用例编号 | 使用独立冒烟编号 |
| 所属模块 | 使用源模块名称 |
| 用例标题 | 描述单一核心目标 |
| 优先级 | 默认 P0 |
| 前置条件 | 写明账号、权限、数据状态和依赖 |
| 测试步骤 | 连续且可执行 |
| 测试数据 | 使用具体、可识别的数据 |
| 预期结果 | 包含页面、数据和权限实际结果 |
| 设计方法/来源 | 记录筛选类型和来源编号 |
| 实际结果 | 留空 |
| 是否通过 | 留空 |
| 备注 | 留空 |

Excel 中增加“筛选说明”工作表，记录：

- 用例总数；
- 各模块用例数量；
- 主要业务链；
- 纳入原则；
- 排除原则；
- 推荐执行顺序。

#### 冒烟用例编号规则
冒烟测试用例使用全局连续编号，不按模块分别重新计数。

格式：

SMK-[ID]

例如：

- SMK-001
- SMK-002
- SMK-003
- SMK-004

编号规则：

- 序号按照最终冒烟用例在冒烟测试集中的顺序全局递增；
- 不因模块变化重新从 001 开始；
- “所属模块”通过独立字段记录，不通过用例编号区分；
- 已生成并稳定使用的编号原则上不因排序变化随意重编号；
- 新增冒烟用例时优先追加新的连续编号。

错误示例：

SMK-LOGIN-001
SMK-USER-001
SMK-ROLE-001

正确示例：

SMK-001
SMK-002
SMK-003

## 接口冒烟测试用例生成

### 转换原则
- 从功能冒烟的业务目标中提取接口依赖链。
- 不逐条翻译页面点击操作。
- 推荐依赖顺序：

`认证 → 用户 CRUD/状态 → 角色 CRUD → 用户角色关联 → 菜单/按钮授权 → 数据权限 → 重新认证或权限查询验证 → 数据清理`

- 一条功能用例可以拆成多个接口步骤。
- 多条功能用例可以合并成一条接口业务链。
- 写接口执行后应通过查询接口或最终业务结果进行验证。
- 接口信息未知时，只填写后置校验目的，不填写接口定义。

### 无接口文档时的硬性规则

当用户没有提供接口文档、抓包信息、后端路由或现有接口用例时：
- 不得推测或编造接口。
- 接口名称留空。
- Method 留空。
- URL 留空。
- Header 留空。
- 请求参数留空。
- 请求体留空。
- HTTP 状态码留空。
- 业务码留空。
- 响应字段及 Schema 断言留空。
- 技术变量名称未知时留空。
- 不得使用占位 URL、示例接口名、猜测状态码、“待补充”或“待抓包”等内容填充单元格。
- 若当前只是缺少接口文档、抓包结果或其他可靠依据，暂时无法确认该字段内容，则保持为空，等待 QA 根据接口文档或抓包结果手工填写。
- 若确认某字段对当前接口不适用或接口本身不存在该部分，则填写“无”，不得留空，也不得为了填满模板而虚构内容。

仍然需要填写：

- 业务目标；
- 所属模块；
- 执行顺序；
- 业务依赖；
- 前置条件；
- 业务测试数据；
- 业务预期结果；
- 后置校验目的；
- 数据清理要求；
- 来源功能用例。

### 空白与“无”的区分
- 空白：表示当前信息尚未确认，后续需要根据接口文档、抓包结果、源码或其他可靠依据补充。
- “无”：表示已确认该字段对当前接口不适用或不存在，无需后续补充。
- 在缺少可靠依据时，AI 不得自行填写“无”。
- “无”只能由 QA 根据接口文档、抓包结果、源码或实际接口行为确认后填写。

若 AI 能从用户已提供的可靠资料中明确确认某字段不存在，可填写“无”；否则保持空白，不得推测。

例如：

- GET 接口已确认无请求 Body → Body 填写“无”；
- 接口已确认无 Query 参数 → Query 参数填写“无”；
- 当前不知道是否存在业务码 → 业务码保持为空；
- 当前尚未获取接口 URL → URL 保持为空。

接口冒烟 Excel 中增加“QA 补充说明”工作表，说明：

- 当前文件属于接口冒烟用例骨架；
- 哪些接口字段需要 QA 填写；
- QA 应根据接口文档、Swagger、抓包信息或后端路由进行补充；
- 接口字段补齐并评审后才能执行。

### 最小性检查

生成后检查：

- 每条用例是否保护一个核心业务能力或关键依赖；
- 删除任一用例是否会导致核心模块、业务链或最终权限校验缺失；
- 是否存在相同业务目标的重复接口骨架；
- 是否误填了没有来源依据的接口信息；
- 是否保留了来源功能用例；
- 是否明确了数据准备和清理要求。
- 冒烟测试不是完整回归测试，不以覆盖所有 P0 用例、所有异常类型或所有功能点为目标。

接口资料未补齐前，交付物必须称为“接口冒烟用例骨架”，不得声明为可直接执行的接口用例。

### 冒烟用例评审

冒烟测试集生成后应进行轻量评审，重点检查：

- 核心主流程是否完整覆盖；
- 关键阻断场景是否遗漏；
- 是否存在重复或低价值用例；
- 是否混入大量回归级场景；
- 前置条件和测试数据是否可稳定准备；
- 单条用例失败时是否能够明确判断是否应阻断后续测试。

冒烟评审以“覆盖核心 + 保持最小”为目标，不要求按完整功能测试用例的粒度逐条深度评审。
