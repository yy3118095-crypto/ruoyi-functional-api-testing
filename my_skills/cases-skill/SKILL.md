# QA 测试用例规划器
从需求文档自动生成专业测试用例，具备深度解析、质量自检能力。
还可用于构建回归测试套件、有效记录 Bug。

> **激活方式：** 此技能仅在明确通过名称调用时触发，例如 `$cases-skill`、`cases-skill` 或 `使用 cases-skill`。

---

## 测试点提取与完善规则
- 测试点应以实际业务功能、页面行为、需求说明、前端校验、后端代码、数据库约束等可确认信息为依据。
- 测试点阶段重点识别正常流程、异常流程、边界值、空值/必填、格式校验、特殊字符、权限、状态变化、数据一致性、重复操作等场景。上述内容属于检查维度，应根据实际功能判断是否适用，不要求每个功能机械覆盖全部维度
- 业务规则在“规则”sheet中定义，关于边界值、长度限制、特殊字符、必填规则、格式规则等不得根据通用经验或模板示例自行假设；若无此区域或缺少对应规则，无法确认时需新建规则列，在规则列中详细说明，并记录为“待确认”。
- 每个测试点应明确对应主要测试设计方法，例如等价类、边界值、场景法、错误推测法等。测试方法应根据测试点主要设计依据判断，不得为追求方法覆盖而机械统一标记。
- 检查原始测试点时，应识别重复、覆盖不足、描述模糊、缺少前置条件或缺少异常场景的测试点
- 测试点阶段只明确“测什么”；具体测试步骤、测试数据、接口地址、请求参数、业务码等在详细测试用例阶段补充。
- 新增、修改、建议删除的测试点应标明变更类型，并新增备注一列，在备注列中说明原因，不得将“变更类型”“变更原因”“待确认说明”等内容写入“测试点”字段。

## 测试用例生成前置检查

在根据测试点生成详细测试用例前，必须先检查最终测试点及其规则依据。

### 可直接生成

满足以下条件时，可生成正式测试用例：

- 测试目标明确；
- 执行所需的关键业务规则已确认；
- 测试数据可以具体确定；
- 预期结果可以明确判断；
- 不依赖尚未确认的关键规则。

### 暂缓生成

若某测试点存在会直接影响测试数据或预期结果的“待确认”规则，则不得为该测试点生成正式测试用例，也不得根据通用经验、示例或模型知识补全。

典型情况包括：

- 字段是否必填尚未确认；
- 最大/最小长度或数值范围尚未确认；
- 字符格式或允许字符尚未确认；
- 状态转换规则尚未确认；
- 权限要求尚未确认；
- 业务成功/失败条件尚未确认。

对于此类测试点：

1. 标记为 `BLOCKED / 待确认`；
2. 输出待确认事项；
3. 说明该规则影响哪些测试用例生成；
4. 待规则确认后再生成对应正式用例。

### 部分生成

如果同一模块中只有部分测试点存在待确认规则：

- 已确认测试点正常生成测试用例；
- 未确认测试点暂缓生成；
- 不得因为局部待确认而阻塞整个模块。

## 测试设计方法

> 详细定义与示例见 [test_design_methods.md](references/test_design_methods.md)

**4 种核心方法根据测试对象特征选择适用方法，必要时组合使用；不得为追求方法覆盖而机械叠加**：

```
等价类划分 / 边界值分析 / 场景法 / 错误推测法
```

| 方法 | 核心动作 | 触发条件 |
|------|---------|---------|
| **等价类** | 划分有效/无效等价类，无效类单独覆盖 | 有输入范围、格式、枚举约束 |
| **边界值** | 测试上点、离点、内点 | 有数值/长度/时间边界 |
| **场景法** | 基本流→备选流→异常流各生成用例 | 涉及多步骤业务流程 |
| **错误推测** | 补充特殊字符、极端值、并发场景 | 高风险模块、历史缺陷多 |

## 需求追溯与覆盖率

> 详细规范见 [test_case_traceability.md](references/test_case_traceability.md)

- **测试点ID**：自动识别 `[MODULE]-NNN` 模式，例如 `ROLE-001`、`USER-001`、`LOGIN-001`。
- **双向追溯**：测试点→用例 + 用例→测试点，Phase 2.8 输出覆盖率统计
- **覆盖率目标**：= 100%，未覆盖需求在预览中高亮警告

## 优先级与回归分类

> 详细规则见 [test_priority.md](references/test_priority.md)

| 级别 | 来源 | 回归集 |
|------|------|--------|
| **P0** 核心 | 基本流用例 | 冒烟测试（每次构建） |
| **P1** 主要 | 备选流 + 边界值 | 核心回归（每日/提测） |
| **P2** 次要 | 异常流 + 错误推测 | 全量回归（发版前） |
| **P3** 边缘 | 边缘错误推测 | 全量回归（发版前） |

## 核心交付物
### 1. 测试点文件完善版
- 测试模块和功能点
- 测试点及对应测试方法
- 测试优先级
- 检查并补充原始测试点文件中考虑不充分或遗漏的场景
- 标识新增、修改或建议删除的测试点，并说明原因

### 2. 手工测试用例
- 用例编号，所属模块和用例标题
- 前置条件和环境准备
- 分步骤说明
- 测试数据要求
- 预期结果，实际结果（空，由 QA 填写）
- 优先级
- 是否通过和备注（空，由 QA 填写）

### 3. 回归测试套件
- 冒烟测试（核心业务关键路径）
- 完整回归（覆盖完整核心业务及既有功能范围）
- 针对性回归（针对特定模块或功能）
- 执行顺序和依赖关系

### 4. Bug 报告
- Bug 标题
- 问题描述
- 环境信息、测试版本和前置条件
- 清晰、连续、可独立执行的复现步骤
- 复现率
- 预期结果和实际结果
- 问题证据
  - 截图：正式提交 Bug 前必须提供；生成阶段若用户尚未提供截图，应记录到“待补充清单”，不得虚构截图或阻塞其他已确认 Bug 的生成。
  - 视频、Console、Network、日志：根据问题类型按需提供
- 严重程度和优先级
- 报告日期
- 开发备注（默认留空，由开发人员填写）
- 当输出为 Excel Bug 报告工作簿时，Sheet 名称、数量、顺序和用途必须严格遵循 [bug_report_templates.md](references/bug_report_templates.md) 中定义的工作簿标准结构。


> 详细规则见 [bug_report_templates.md](references/bug_report_templates.md)

### 5. 待确认清单

用于测试点和测试用例生成阶段，记录会影响测试数据或预期结果判断的未确认业务规则。

- 用例编号
- 关联测试点ID
- 用例标题
- 待确认事项
- 规则确认后同步更新测试用例和追溯矩阵

> 详细规则见 [test_to_case_rules.md](references/test_to_case_rules.md)

### 6. Bug 待补充清单

仅在生成 Bug 报告时使用，用于记录已确认 Bug 尚缺少的提交信息，例如：
- 截图
- 浏览器具体版本
- 环境信息
- 复现率
- Console / Network / 日志
- 实际结果补充说明

Bug 待补充信息不得与“业务规则待确认”混为一类。

## 反模式

| 避免 | 原因 | 替代做法 |
|-------|-----|---------|
| 模糊的测试步骤 | 无法复现 | 明确操作 + 预期结果 |
| 缺少前置条件 | 测试可能意外失败 | 记录所有环境准备要求 |
| 没有测试数据 | 测试人员无法继续 | 提供示例数据或生成方式 |
| 测试数据命名无统一规则 | 难以识别数据用途，影响执行和维护| 使用统一、可读、可追踪的测试数据命名规则 |
| 笼统的 Bug 标题 | 难以跟踪 | 具体描述："[功能] 在 [操作] 时出现问题" |
| 跳过边界场景 | 可能遗漏关键 Bug | 覆盖边界值、空值、非法值、重复值、特殊字符及异常业务场景 |
| 根据现象直接推测 Bug 根因 | 容易产生错误结论 | 实际结果只描述观察现象，根因由进一步排查确认 |
| 缺少 Bug 复现率 | 无法判断问题稳定性 | 记录必现、偶现或具体复现次数 |
| Bug 无截图证据 | 难以确认实际现象 | 每个 Bug 至少提供 1 张有效截图 |
| 所有 Bug 强制填写 Console/Network/日志 | 产生大量无效信息 | 根据问题类型按需提供，无关字段直接省略 |
| 预期结果依赖未知规则 | 可能错误判定 Bug | 无明确依据时标记“待确认”，不得自行假设 |

## 验证检查清单

**测试用例：**
- [ ] 用例标题与当前操作类型一致；
- [ ] 每一步都有预期结果
- [ ] 实际结果、是否通过、备注在生成阶段保持空白。
- [ ] 已记录前置条件
- [ ] 测试数据可用
- [ ] 已分配优先级

**Bug 报告：**
- [ ] Bug 标题具体、明确，能够快速识别功能和异常现象
- [ ] 问题描述与实际测试现象一致，未推测未经确认的根因
- [ ] 已记录必要的环境、版本和前置条件
- [ ] 复现步骤完整、连续且可独立执行
- [ ] 预期结果有明确依据
- [ ] 实际结果与实际观察现象一致
- [ ] 已提供至少 1 张能够证明问题的截图；若当前尚未提供，已记录至待补充清单
- [ ] Console、Network、日志或视频等证据已根据问题类型按需补充
- [ ] 已记录复现率
- [ ] 已分别设置严重程度和优先级
- [ ] 无法确认的信息已标记为“待确认”，未自行补全

## 手工测试用例生成

生成测试用例时必须遵循：
- 每条用例仅验证一个核心测试目标
- 每条测试用例原则上只包含一个无效等价类，确保异常原因可以独立定位。
-多个无效条件的组合场景应单独设计为组合测试用例，不应替代单一无效等价类用例。
- 每一步必须有明确预期结果
- 测试数据必须具体且可执行
- 实际结果、是否通过、备注由 QA 执行后填写
- 输出格式参考 [测试用例模板](references/test_case_templates.md)

## 完整功能测试用例工作簿说明

生成完整功能测试用例 Excel 时，必须生成“使用说明”工作表，并将其放在工作簿第一位。

“使用说明”必须包含：
- 测试范围；
- 测试用例总数及各优先级数量；
- 测试点总数；
- 本次范围外测试点数；
- 已覆盖和未覆盖测试点数；
- 测试点覆盖率；
- 孤儿用例数；
- 遗留问题。

具体结构和填写规则遵循 [test_case_templates.md](references/test_case_templates.md) 中的“用例工作簿：使用说明Sheet”。

追溯检查产生的统计结果必须写入最终Excel，不得只在生成过程或回复中展示。

## 已有功能测试用例标准化
当用户要求整理、转换或统一已有功能测试用例时：
- 读取用户提供的 Excel 测试用例；
- 按 test_case_templates.md 中的完整功能测试用例结构进行整理；
- 保留原用例的测试目标、前置条件、测试步骤、测试数据和预期结果；
- 原用例编号写入“来源用例编号”，新用例编号统一使用 Case-[MODULE]-NNN；
- 原字段能够直接对应标准字段时进行映射，不得随意改变原意；
- 缺少的内容只有在源文件或已确认规则中有依据时才能补充，否则留空；
- 原编号存在重复或跳号时进行覆盖、删除或重排，且在“使用说明”的“遗留问题”中记录；
- 检查测试点覆盖情况、孤儿用例和关联异常；
- 生成“使用说明”“测试用例”和“追溯矩阵”工作表；
- 转换结果另存为 原文件名_标准化版.xlsx，不得覆盖原文件。
如果原文件没有测试点或无法确认用例与测试点的关系，“关联测试点ID”留空，并将对应条目标记为孤儿用例，不得推测关联。



## 功能测试用例评审
当用户要求评审已有功能测试用例时：
1. 读取原测试用例，以及配套的测试点、规则和数据准备。
2. 按 [测试点追溯与覆盖率](references/test_case_traceability.md) 检查：
   - 测试点覆盖率；
   - 未覆盖测试点；
   - 孤儿用例；
   - 测试点与用例的双向追溯关系。
3. 同时检查：
   - 标题与测试目标是否一致；
   - 前置条件是否完整；
   - 步骤是否连续且可执行；
   - 测试数据是否具体、可准备、可清理；
   - 预期结果是否明确且可以判断；
   - 是否存在重复、冗余或目标重叠用例；
   - 优先级是否符合业务风险；
   - 业务规则是否有明确依据。
   - 必须将孤儿用例和关联异常写入最终 Excel，不得只在生成过程或统计结果中识别。
4. 实际结果、是否通过和备注应保持空白，由 QA 执行后填写。
5. 无法确认的业务规则标记为“待确认”，不得自行假设。
6. 默认输出评审结论和问题清单；用户要求修改时，另存为新的完善版 Excel。


## 基于测试执行结果生成 Bug 报告

当用户提供已执行的测试用例文件并要求生成 Bug 报告时：

- 仅将 `是否通过 = 失败 / fail / failed / 不通过` 的用例视为 Bug 候选。
- `是否通过 = 通过 / pass / passed` 的用例不得生成 Bug。
- `是否通过` 为空时，视为尚未执行，不得作为 Bug。
- 判断“是否通过”时忽略前后空格及英文字母大小写差异。
- 因业务规则不明确导致的 `BLOCKED / 待确认`，进入“待确认清单”。
- 因截图、环境、复现率、Network、Console 等 Bug 提交信息缺失导致的信息不完整，进入“Bug 待补充清单”。
- `无法执行` 的用例不得自动判定为 Bug；应记录无法执行原因，并根据原因进入对应清单。
- `是否通过` 仅用于识别 Bug 候选，不得仅根据“失败”自行推测异常现象。
- Bug 实际现象应优先依据“实际结果”，备注用于补充执行情况、复现信息、证据及排查说明。
- 前置条件、测试数据、复现步骤、预期结果应优先复用原测试用例内容。
- 多条失败用例若反映同一个实际问题，应归并为同一个 Bug，不得按照失败用例数量机械生成 Bug。
- 一条失败用例若实际包含多个相互独立的问题，可在证据充分时拆分为多个 Bug。
- 原失败用例内容必须保留用于追溯，不得因生成 Bug 报告而修改。

## 功能冒烟测试用例生成
当用户要求生成、提取或更新功能冒烟测试时：
- 必须读取 冒烟测试编写规则 的“功能冒烟测试用例生成”部分。
- 默认读取本 Skill 的 cases/*.xlsx；用户另行指定文件时，以用户提供的文件为准。
- 基于已有功能用例提取最小冒烟集，非必要不重新生成完整功能用例。
- 仅在必要时增加缺失的核心功能场景，避免生成大量重复或低价值的冒烟用例，若增加缺失场景，需说明理由。
- 优先覆盖 P0、核心 CRUD、认证与授权、关键状态变化及跨模块主流程。
- 合并验证目标相近且可以连续执行的场景，排除大量边界、低收益异常和重复场景。
- 保留来源用例编号或测试点编号，生成可追溯、可按顺序执行的 Excel。
- 实际结果、是否通过和备注保持空白，由 QA 执行后填写。
具体参考 [冒烟测试编写规则](references/smoke_case.md)

## 接口冒烟测试用例生成

当用户要求基于功能用例生成接口冒烟测试时：

- 必须读取冒烟测试编写规则中的“接口冒烟测试用例生成”部分。
- 从功能冒烟集中提取接口业务链，按照“认证 → 核心 CRUD → 用户角色关联 → 授权 → 权限生效验证 → 数据清理”组织。
- 不得将每条功能用例机械地一对一转换为接口用例。
- `cases/` 中的文件只提供功能测试依据，不视为接口文档。
- 没有接口文档、抓包、后端路由或现有接口用例时，不得推测 Method、URL、Header、请求参数、请求体、HTTP 状态码、业务码或响应字段。
- 接口专属字段在无法确认时保持为空，由 QA 根据接口文档、抓包、源码或实际请求补充；不得写入猜测值、示例值、“待补充”或“待抓包”等占位内容。
- 若 QA 已明确确认某字段对当前接口不存在或不适用，可填写“无”；在没有可靠依据时，AI 不得自行填写“无”。
- 可以从功能用例确认的业务目标、前置条件、依赖关系、测试数据、业务预期、后置校验和数据清理要求应正常填写。
- 实际结果、是否通过和备注保持空白。

具体参考 [冒烟测试编写规则](references/smoke_case.md)

---

### 阶段1：接口骨架生成

缺少接口资料时，仅根据已确认的业务流程生成接口测试骨架。

不得猜测以下技术信息：

- Method；
- URL；
- Header；
- Path 参数；
- Query 参数；
- Body；
- HTTP 状态码；
- 业务码；
- 响应字段；
- Schema；
- 技术变量名称。

未确认字段保持空白。

骨架阶段仍应填写能够从功能测试依据中确认的内容，包括：

- 业务目标；
- 所属模块；
- 接口业务链顺序；
- 前置条件；
- 业务依赖；
- 测试数据；
- 预期业务结果；
- 后置校验；
- 数据清理要求。

---

### 阶段2：QA补充后的正式化

QA 根据接口文档、抓包、源码或实际请求补充真实接口技术信息后，可再次将文件交给 AI。

AI 应仅基于 QA 已补充或其他可靠依据中已确认的真实接口信息进行完善：

- 检查并完善请求信息；
- 完善 HTTP 状态码、业务码和响应字段断言；
- 检查上游接口提取变量与下游接口引用变量是否一致；
- 检查接口依赖和业务链执行顺序；
- 检查空白字段和“无”的使用是否合理；
- 检查是否仍存在未经确认的猜测内容；
- 补充必要的列表、详情、状态、权限或最终业务结果校验；
- 检查数据清理是否完整。

不得覆盖 QA 已确认的真实接口信息，除非发现明确冲突；存在冲突时应标记为待确认，不得擅自修改。

对于仍缺少可靠依据的接口字段：

- 继续保持空白；
- 不得为了形成“完整用例”而自行补全；
- 若缺失内容会导致用例无法实际执行，则该用例应标记为“待确认”或“未正式化”。

仅当执行所需的关键接口信息和断言规则均已确认后，才可输出为正式可执行接口测试用例。
